# API внешних коннекторов Scheduler v1

API внешних коннекторов — расширенный режим для владельца, который самостоятельно размещает и запускает
внешний парсер. Он позволяет предложить полный снимок расписания,
не получая доступ к базе Scheduler. Снимок проходит валидацию, сравнение с
доверенной версией, карантин и только затем публикуется.

## Жизненный цикл

1. Администратор создаёт коннектор в разделе **Коннекторы**.
2. Мастер один раз показывает `connector_id`, `key_id` и закрытый ключ Ed25519.
3. Коннектор переводится в `testing` и отправляет тестовый снимок.
4. Администратор переводит интеграцию в состояние `pending_review`, открывает тестовый снимок в разделе
   **Источники**, изучает визуальное сравнение и одобряет его для активации. Одобрение получает статус
   `approved` и не меняет рабочее расписание, метаданные вуза или семестры.
5. После одобрения коннектор можно перевести в `active`. Scheduler одной транзакцией приостанавливает
   прежний активный источник вуза, активирует новый, применяет снимок, обновляет метаданные и создаёт
   уведомления. Частично выполненное переключение невозможно.
6. Последующие корректные снимки публикуются автоматически. Аномальные
   остаются в карантине.

У одного учебного заведения может быть только один источник в состоянии `active`.
Предварительно приостанавливать прежний источник не нужно: это является частью атомарной активации.
Публикации разных источников одного вуза сериализуются на уровне PostgreSQL, а уже приостановленный
источник не может повторно опубликовать старый снимок.
Значения `odd` и `even` считаются от `term.starts_on`: первая неделя семестра —
нечётная. При приёме снимка они преобразуются в явный двухнедельный цикл, поэтому
выдача расписания и напоминания используют одинаковую чётность.

Состояния: `draft → testing → pending_review → active` («черновик → тестирование → проверка → активен»). Активный коннектор
можно приостановить, вернуть в тестирование или архивировать. Архив не удаляет
историю и снимки: коннектор можно вернуть в `draft`, после чего он снова проходит
тестирование и проверку перед активацией.

## Контракт

- JSON-схема: [`schema/schedule-snapshot-v1.json`](schema/schedule-snapshot-v1.json)
- описание OpenAPI: [`openapi/connector-v1.yaml`](openapi/connector-v1.yaml)
- пример: [`examples/connector-snapshot-v1.json`](examples/connector-snapshot-v1.json)
- SDK для Go: пакет `connector/v1`
- командная строка: `go run ./cmd/connector`
- SDK для Python: `sdk/python`

Основной запрос:

```text
POST /api/v1/connectors/{connector_id}/snapshots
```

Снимок всегда описывает полное актуальное состояние одного учебного заведения и одного
учебного периода. При публикации рабочий набор занятий вуза заменяется целиком, поэтому записи
предыдущего семестра не смешиваются с новым расписанием. История остаётся в JSON опубликованных снимков.
Один снимок может содержать не более 5 000 групп и 50 000 занятий. Публикация выполняется
пакетными SQL-вставками; превышение лимита отклоняется до постановки задания в обработку.

Если разработчик готов передать код парсера проекту, отдельный сервер и этот API не нужны — удобнее
использовать [управляемый парсер](managed-parsers.md). ИВГПУ в основной поставке является примером
именно такого режима.

## Подпись

Каждый запрос подписывается Ed25519. Каноническая строка:

```text
HTTP_METHOD\n
ESCAPED_PATH\n
RFC3339_TIMESTAMP\n
NONCE\n
SHA256_OF_TRANSPORT_BODY
```

Обязательные заголовки:

```text
X-Scheduler-Key-ID
X-Scheduler-Timestamp
X-Scheduler-Nonce
X-Scheduler-Content-SHA256
X-Scheduler-Signature
Idempotency-Key                    # для отправки снимка
```

Подпись и SHA-256 рассчитываются по телу в том виде, в котором оно передаётся.
При `Content-Encoding: gzip` подписываются сжатые байты. После проверки подписи
сервер ограничивает и размер распакованного JSON.

Метка времени допускает расхождение не более пяти минут. Значение `nonce` одноразовое.
Повторный `snapshot_id` или `Idempotency-Key` возвращает существующую загрузку,
не создавая дубликат.
Для отправки снимка `Idempotency-Key` должен совпадать с его `snapshot_id`; это исключает
неоднозначность при повторных запросах из разных SDK.

Внутренний worker получает задание по аренде с уникальным claim-token и продлевает её каждые
30 секунд. Завершить или повторно поставить задание может только текущий владелец аренды. Если
процесс остановлен, lease истекает и задание безопасно забирает другой экземпляр; поздний ответ
старого worker не способен перезаписать новый результат.

## Командная строка

```bash
go run ./cmd/connector validate snapshot.json
go run ./cmd/connector push connector.json snapshot.json
go run ./cmd/connector status connector.json RUN_ID
go run ./cmd/connector heartbeat connector.json
```

`connector.json`:

```json
{
  "base_url": "https://admin.example.org",
  "connector_id": "connector-…",
  "key_id": "key-…",
  "private_key": "…"
}
```

Закрытый ключ нельзя добавлять в Git. При утрате или компрометации выпустите новый в
админке — старый перестанет работать немедленно.

## Повторные попытки

- `202` — снимок принят в долговечную очередь;
- `200` — такой снимок уже был принят;
- `401` — неверная подпись, метка времени или идентификатор ключа;
- `409` — повторное значение `nonce` либо недопустимое состояние;
- `413` — превышен лимит;
- `422` — снимок не соответствует контракту;
- `429` — превышено ограничение частоты запросов;
- `5xx` — временная ошибка сервиса.

На сетевые ошибки и `5xx` следует повторять тот же снимок с тем же
`Idempotency-Key`, но с новой меткой времени и новым `nonce`. Используйте экспоненциальную
задержку со случайным отклонением. SDK для Go и Python выполняют такие повторы автоматически, включая `429` и
уважение числового заголовка `Retry-After`.

## Совместимость

В `schema_version=1.0` могут добавляться только необязательные поля. Коннектор
не должен зависеть от неизвестных полей ответа. Несовместимый контракт будет
опубликован отдельной версией URL и схемы.

## Порядок приёма и терминальные статусы v1

Ответы приёма и проверки задания содержат `ingestion_sequence` — монотонный номер,
назначенный сервером для источника. Публикации упорядочены по приёму снимков
сервером. `generated_at` описывает время формирования документа и не определяет
порядок публикаций. Повтор idempotency key сохраняет исходные номер и результат;
пропуски номеров допустимы.

`superseded` — терминальный результат: более новый принятый снимок уже опубликован.
Старое задание больше не публикуется и не создаёт уведомлений. SDK/CLI должны показывать
этот результат, а не бесконечно повторять задание. Ручной откат аудируется отдельно и
не уменьшает номер последней автоматической публикации. После обновления источнику с
неоднозначным историческим порядком нужен новый снимок; повтор старого ключа не поможет.

## Проверка документа до отправки

Проверяйте снимок средствами Go SDK (`connector/v1.Validate`), Python SDK
(`validate_snapshot`) или командой `validate` соответствующего CLI.
При использовании JSON Schema включите проверку `format`; например, в Python
`jsonschema` передайте `FormatChecker`. Одна проверка структуры не проверяет все
ограничения дат и URL. Неизвестные поля снимка версии `1.0` допускаются;
в административном API неизвестные поля запрещены.

Семантические ограничения, которые дополнительно проверяют SDK и сервер:

- обязательные непустые названия вуза, периода, группы и занятия; известные поля имеют
  точные JSON-типы, `null` не подменяет пропущенное поле;
- `generated_at` — RFC3339 с `Z` или явным смещением; не более десяти минут в будущем;
- timezone — существующая IANA-зона; `schedule_url`, если задан, — абсолютный HTTP(S) URL;
- начало периода не позже конца; точная дата и границы повторения находятся внутри периода;
- время занятия имеет формат `HH:MM`, начало раньше окончания;
- ID групп и занятий уникальны; названия групп уникальны после нормализации регистра и пробелов;
- 1–5000 групп, максимум 50000 занятий; пустой список занятий отдельной группы разрешён;
- цикл 2–16 недель, непустой набор уникальных позиций 1–cycle_length; обе границы
  повторения задаются вместе. Чётность определяется от `term.starts_on`.

JSON pull получает **тот же полный документ**, что и push: institution, term,
generated_at, группы и занятия. Дата запуска загрузки не переопределяет период.
Идентичности согласуются с существующими группами и занятиями, чтобы сохранить подписки
и overrides. Настройки существующего вуза из черновика применяются при атомарной активации.

## Контракты административного редактора

`recurrence` возвращается при чтении и принимается при изменении занятия. При отсутствии
поля сохраняется правило существующей записи. Для изменения режима/семестра передайте
правило явно; `{}` обозначает обычное правило выбранного режима. Для новых odd/even
сервер создаёт двухнедельный цикл от начала семестра. Историческая первая дата занятия
не переносится на начало семестра при обычном редактировании.

`POST /api/editor/preview` принимает `{lesson, lesson_id?, from, days}`; `from` — дата,
`days` — 1–112. Ответ содержит фактические даты и правило. Календарный экспорт
`GET /api/editor/calendar?group=...&from=...&days=...` применяет ту же календарную функцию.

`GET /api/connectors/{id}/activation` возвращает сравнение для активации. Новый клиент
передаёт в PATCH `snapshot_id` и `expected_current_snapshot_id`; сервер отклоняет устаревшее
сравнение кодом 409. Одобрение кандидата и публикация работающего расписания — разные действия.
