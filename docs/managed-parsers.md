# Управляемые парсеры Scheduler v1

Управляемый парсер — рекомендуемый способ добавить новое расписание. Автор пишет только код,
который умеет прочитать конкретный источник. Запускать отдельный сервер, контейнер или планировщик ему не
нужно: после проверки кода парсер собирается вместе с Scheduler и выполняется общим обработчиком парсеров.

## Что реализует автор

Публичный пакет `parser/v1` не зависит от PostgreSQL и пакетов `internal`. Парсер предоставляет
описание, стабильный список групп и расписание одной группы:

```go
type Parser interface {
    Manifest() Manifest
    FetchGroups(ctx context.Context) ([]Group, error)
    FetchSchedule(ctx context.Context, externalGroupID string) ([]Lesson, error)
}
```

- `Manifest` описывает идентификатор парсера, версию, учебное заведение, ответственного и обычный интервал;
- `Group.ExternalID` берётся из источника и не меняется при переименовании группы;
- `Lesson.ExternalID` стабилен для одного занятия;
- даты, чётность и циклы используют общую модель `connector/v1`, поэтому встроенные и внешние
  интеграции одинаково понимаются ботом и админкой;
- методы обязаны учитывать отмену `ctx` и не записывают данные в базу самостоятельно.

## Что делает Scheduler

После регистрации фабрики платформа создаёт новый экземпляр парсера для каждого запуска и берёт
на себя:

1. периодический запуск по `data_sources.update_interval`;
2. запрет одновременного запуска одного источника через консультативную блокировку PostgreSQL;
3. ограниченный параллелизм запросов расписания групп и независимый таймаут каждого источника;
4. повтор временных ошибок и досрочную остановку при серии одинаковых ответов;
5. нормализацию стабильных идентификаторов и проверку структуры;
6. создание полного кандидата-снимка;
7. сравнение с последним доверенным снимком;
8. карантин резкого удаления или роста данных;
9. транзакционную публикацию и уведомления подписчиков;
10. логи, диагностику ответов, метрики и ручной запуск из админки.

Источники разных вузов запускаются ограниченно параллельно. На один вуз допускается только
один активный источник, а публикация защищена отдельной блокировкой по идентификатору вуза.

## Порядок добавления

1. Создайте пакет `integrations/<parser-id>`.
2. Реализуйте `parser/v1.Parser` и фабрику `New`.
3. Добавьте модульные тесты преобразования и необязательный тест настоящего источника, включаемый переменной окружения.
4. Зарегистрируйте фабрику в `cmd/bot/main.go` и `cmd/admin/main.go` как
   `managed:<parser-id>`, а описание — в каталоге админки.
5. Отправьте запрос на слияние. Не добавляйте токены, cookie, дампы ответов с персональными данными и
   зависимости от `internal/`.
6. После сборки выберите установленный парсер в мастере: `Интеграции → Подключить источник →
   Управляемый парсер`.
7. Переведите интеграцию в тестирование, нажмите «Запустить тест», откройте снимок в «Источниках» и
   одобрите его. Одобренный снимок ещё не виден пользователям: рабочие данные заменяются только при
   активации интеграции, одновременно со сменой активного источника.

## Пример ИВГПУ

[`integrations/ivgpu`](../integrations/ivgpu) получает официальный список групп и расписание по
точным датам. В пакете нет доступа к БД, кода публикации, фонового цикла или ключей: всё это уже
предоставляет Scheduler. Проверка на настоящем источнике запускается явно:

```powershell
$env:IVGPU_INTEGRATION_TEST='1'
go test ./integrations/ivgpu -run TestLiveIVGPUManagedParser -v -count=1
```

## Когда нужен другой режим

- Если уже существует публичный HTTPS-адрес со снимком версии 1 — используйте получение JSON без кода.
- Если владелец не может передать код, сам определяет момент отправки или источник доступен только в
  его сети — используйте [API внешних коннекторов](connector-api.md).
