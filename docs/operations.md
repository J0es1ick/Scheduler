# Эксплуатация Scheduler

## Режим окружения

Для локальной разработки используйте `DEPLOYMENT_ENV=development`. Перед публичным запуском
установите `DEPLOYMENT_ENV=production`: приложение тогда не запустится с небезопасным режимом
PostgreSQL, HTTP-адресом альтернативного Telegram API, отключённым Secure-флагом cookie или
некорректным публичным адресом админки. База production-окружения должна использовать
`DATABASE_SSLMODE=require`, `verify-ca` или `verify-full`.

Встроенный PostgreSQL из `docker-compose.yml` предназначен для локальной разработки и не включает
TLS. Для production задайте `DATABASE_CONTAINER_HOST`, `DATABASE_CONTAINER_PORT` и безопасный
`DATABASE_CONTAINER_SSLMODE` для внешнего PostgreSQL с TLS; Compose передаст их процессам
приложения как обычные `DATABASE_HOST`, `DATABASE_PORT` и `DATABASE_SSLMODE`. Отдельные переменные
без суффикса `CONTAINER` остаются настройками запуска Go-процессов непосредственно на хосте.

`postgres-bootstrap` использует те же адрес, порт и SSL-режим, поэтому при заданном внешнем хосте
роли и права создаются именно во внешней БД, а не во встроенном контейнере. Для `verify-ca` и
`verify-full` при необходимости задайте контейнерные пути `PGSSLROOTCERT`, `PGSSLCERT` и `PGSSLKEY`.
Compose передаёт только пути; сертификаты и закрытый клиентский ключ подключайте read-only volume или
Docker secret ко всем сервисам, которые подключаются к этой БД: `postgres-bootstrap`, `migrator`,
`bot`, `admin`, `site` и `backup`. Закрытый ключ не следует хранить в `.env` или
передавать содержимым переменной окружения. Backup и проверка восстановления передают
`DATABASE_SSLMODE` в libpq через `PGSSLMODE`, поэтому `pg_isready`, `pg_dump`, `psql`, `createdb`,
`dropdb` и `pg_restore` используют одну TLS-политику.

При работе с внешней БД встроенный PostgreSQL запускать не требуется. После создания самой БД,
настройки подключения, сертификатов и внешнего хранилища резервных копий выполните сервисы явно:

```powershell
docker compose build app-image backup
docker compose run --rm --no-deps postgres-bootstrap
docker compose run --rm --no-deps migrator
docker compose up -d --no-deps bot admin site backup
```

Следующий шаг выполняйте только после успешного завершения предыдущего. В этом варианте
`--no-deps` намеренно отключает локальную цепочку зависимостей; обычный `docker compose up`
остаётся сценарием с встроенным PostgreSQL.

## Административный доступ

Основной рабочий вход выполняется через Telegram Mini App. Сервер проверяет подпись `initData` и
актуальную роль администратора при каждом защищённом запросе.

Вход по общему ключу предназначен только для первоначальной настройки и аварийного локального
доступа:

```env
ADMIN_ACCESS_LOGIN_ENABLED=false
ADMIN_ACCESS_TOKEN=<случайный-секрет>
```

Для первоначальной настройки временно установите `ADMIN_ACCESS_LOGIN_ENABLED=true`, войдите,
назначьте Telegram-администратора и снова выключите флаг. Сессии хранятся в PostgreSQL в виде
SHA-256-хешей: само значение cookie в базу не попадает. Telegram-сессии переживают перезапуск и при
каждом защищённом запросе повторно сверяют актуальную роль. Сессии, созданные по общему ключу,
принудительно отзываются при каждом запуске административного процесса.

`ADMIN_COOKIE_SECURE` задаётся явно. Для публичного HTTPS всегда используйте `true`; `false`
допустим только для локального `http://127.0.0.1`.

## Обратный прокси

Docker Compose по умолчанию публикует админку и сайт только на `127.0.0.1`. Для обратного прокси,
запущенного на том же хосте, это безопасная рекомендуемая настройка. Если прокси работает в
отдельном контейнере, подключите его к общей сети Docker или осознанно измените
`ADMIN_BIND_ADDRESS` и `SITE_BIND_ADDRESS`, одновременно ограничив доступ сетевым экраном.

`X-Forwarded-For` и `CF-Connecting-IP` учитываются только тогда, когда непосредственный адрес
соединения входит в `ADMIN_TRUSTED_PROXY_CIDRS`. Укажите CIDR каждого доверенного прокси через
запятую: цепочка `X-Forwarded-For` проверяется справа налево до первого недоверенного адреса.
Прокси должен перезаписывать полученные от клиента `X-Forwarded-For` и `CF-Connecting-IP`, а не
передавать их без проверки. Не добавляйте `0.0.0.0/0` или `::/0`.

Для Connector API на прокси установите ограничение тела не выше настроенного для коннектора
`max_payload_bytes`, таймаут чтения тела и предел одновременных соединений с одного адреса.
Приложение повторно ограничивает сжатое и распакованное тело, а счётчик запросов коннектора
обновляется атомарно, но сетевые соединения выгоднее отбрасывать до Go-процесса.

## Метрики

HTTP-адрес `/metrics` требует отдельный токен доступа:

```powershell
$headers = @{ Authorization = "Bearer $env:ADMIN_METRICS_TOKEN" }
Invoke-WebRequest http://127.0.0.1:18080/metrics -Headers $headers
```

Не используйте `ADMIN_ACCESS_TOKEN` как токен метрик. На внешнем обратном прокси также рекомендуется
полностью закрыть `/metrics` от публичной сети.

Метрики `scheduler_reminder_worker_*` показывают время и продолжительность последнего запуска,
число обработанных получателей и ошибок, время последнего полного обхода и наличие сохранённого
курсора. Те же сведения доступны администраторам в Telegram через `/metrics`. Курсор хранится в
PostgreSQL, поэтому незавершённый обход продолжается при следующем запуске обработчика и после
перезапуска бота.

Очередь внешних коннекторов с отправкой данных отражается метриками
`scheduler_connector_queue{status=...}`. Метрика `scheduler_storage_bytes` показывает полный размер
БД, объём JSON входящих коннекторов и снимков. Управляемые парсеры и получение JSON наблюдаются общими
метриками запусков источников. Рост `failed` или длительное накопление `pending` означает, что нужно
открыть раздел «Интеграции», посмотреть конкретную отправку и проверить контракт или доступность
обработчика.

Для ручной проверки репозиториев используйте отдельную тестовую базу:

```powershell
$env:TEST_DATABASE_URL = "postgres://postgres:password@127.0.0.1:55432/scheduler_test?sslmode=disable"
go test -p 1 -tags=integration ./internal/database ./internal/repository ./internal/admin ./internal/connectorapi ./internal/site -count=1
```

Интеграционный тест создаёт временные записи и удаляет их после проверки, но запускать его против
рабочей базы всё равно не следует. Пакеты используют общие очереди и выполняются последовательно
(`-p 1`), чтобы тестовый воркер одного пакета не забирал события другого.

## Ограничение нагрузки бота

`BOT_MAX_CONCURRENT_HANDLERS` ограничивает общее число одновременно выполняемых обработчиков, а
`BOT_MAX_PENDING_PER_SENDER` — число ожидающих команд одного пользователя или чата. После
исчерпания любого лимита новое событие немедленно отклоняется и не оставляет ожидающую горутину.
Ожидающие команды одного отправителя не занимают глобальные слоты, поэтому один активный
пользователь не может вытеснить остальных. Для небольшого запуска подходят значения `32` и `8`.
Счётчик отклонений доступен как `scheduler_telegram_handler_rejections_total`.

Персональная кнопка Mini App синхронизируется при первом запуске, изменении роли пользователя
или изменении `ADMIN_PUBLIC_URL`. Успех и постоянные ответы Telegram `400`, `403` и `404`
фиксируются отдельно для пользователя; временная ошибка оставляет только его в очереди повтора.
Поэтому заблокировавший бота пользователь не вызывает полный обход базы каждые 30 секунд.

`/ready` требует не только доступную PostgreSQL и живые фоновые процессы. Каждый зарегистрированный
воркер должен завершить хотя бы один проход. Ошибка внутренней инфраструктуры или остановившийся
воркер переводят процесс в `not_ready`. Ошибка отдельного внешнего сайта расписания возвращает HTTP
200 со статусом `degraded`: бот продолжает отдавать последний доверенный снимок, а оркестратор не
запускает бесполезный цикл перезапусков.

Compose smoke в CI обращается именно к `/ready`. Для независимости от внешнего Telegram в CI
запускается локальная заглушка Bot API через профиль `ci`; адрес передаётся в
`BOT_TELEGRAM_API_URL`, а HTTP явно разрешается через `BOT_TELEGRAM_API_ALLOW_INSECURE=true`.
Этот флаг допустим только для изолированной локальной заглушки. В рабочем окружении обе переменные
оставляйте пустыми: тогда используется официальный Telegram Bot API.

## Восстановление публикаций при обновлении

В Compose роли создаёт одноразовый `postgres-bootstrap`, а миграции и восстановление публикаций
выполняет отдельный одноразовый сервис `migrator`. `bot`, `admin`, `site` и `backup` запускаются
только после их успешного завершения. Обычные процессы выполняют только read-only-проверку:
убеждаются, что применены все встроенные миграции, совпадают SHA-256 и очередь восстановления пуста.
Они не имеют DDL-прав и не пытаются конкурировать за длительное восстановление. Каждая применённая миграция хранит SHA-256; изменение уже применённого SQL
останавливает запуск. Частичная legacy-схема не принимается за завершённую миграцию 001.

Миграция `026_publication_reconciliation_queue.up.sql` исправляет именно состояние, оставленное
ранее применённой миграцией 025. Она восстанавливает указатель единственного приостановленного
источника, а при наличии конкурирующего активного источника создаёт одноразовую задачу восстановления
из его уже опубликованного текущего снимка. Обычный новый `approved`-кандидат в очередь не попадает.

До успешного восстановления процессы не начинают обслуживать запросы. Задачу атомарно
захватывает только `migrator`; остальные процессы сообщают, что сначала нужно завершить migrator job.
Завершённая запись удаляется, поэтому она не удерживает снимок от очистки истории. При ошибке задача,
её число попыток и диагностика остаются в таблице. Повторная публикация сохраняет `lesson_overrides`,
исходные `published_at`, `last_success_at`, `last_run_at`, а также `last_error`,
`consecutive_failures` и `next_retry_at`. Поэтому восстановление не выглядит как новый успешный запуск
парсера, не стирает диагностику и не сбрасывает действующую задержку перед повторной попыткой.

Проверить незавершённые восстановления можно запросом:

```sql
SELECT university_id, snapshot_id, attempts, claimed_at, last_error, created_at
FROM publication_reconciliation_queue;
```

Миграция намеренно не угадывает прежний `current_snapshot_id` у архивного или приостановленного
источника, если у вуза нет действующего источника: автоматическая публикация такого кандидата была
бы опаснее сохранения текущих рабочих данных.

## Резервные копии

Compose-сервис `backup` создаёт резервные копии PostgreSQL в специальном формате сразу после
запуска и далее с интервалом `BACKUP_INTERVAL_SECONDS`. Файлы и SHA-256 хранятся в отдельном томе
`pgbackups`; срок хранения задаётся `BACKUP_RETENTION_DAYS`. Локальное создание и отправка во
внешнее хранилище имеют отдельные маркеры здоровья. После локальной ошибки новая попытка выполняется
через `BACKUP_RETRY_SECONDS` (по умолчанию пять минут), а не через полный суточный интервал.

Проверка выполняет настоящее восстановление последней копии во временную базу и сверяет точный
список и SHA-256 всех миграций с текущим release image:

```powershell
.\scripts\verify-backup.ps1
```

Резервная копия содержит схему и данные, но не привязанные к конкретному окружению ACL PostgreSQL.
При проверочном и аварийном восстановлении права из старых архивов также пропускаются. После
восстановления `postgres-bootstrap` заново приводит роли и разрешения к декларативному состоянию;
это позволяет переносить одну копию между окружениями и не требует выдавать restore-роли права
изменять default privileges роли migrator.

Эксплуатационная цель для стандартной конфигурации: **RPO не более 24 часов** и **RTO не более
60 минут**. Уменьшение `BACKUP_INTERVAL_SECONDS` прямо уменьшает RPO. Проверку восстановления нужно
выполнять после изменения схемы и не реже одного раза в месяц.

В production обязательна зашифрованная копия вне хоста. Подключите внешнее/NAS/S3-FUSE-хранилище
к контейнеру, создайте отдельную пару ключей `age` и передайте backup-процессу только публичный
recipient:

```env
BACKUP_OFFSITE_DIRECTORY=/offsite
BACKUP_AGE_RECIPIENT=age1...
BACKUP_REQUIRE_OFFSITE=true
```

Identity создаётся один раз командой `age-keygen -o backup_age_identity`; выведенный публичный
recipient задаётся через `BACKUP_AGE_RECIPIENT`. Сам identity-файл должен находиться в отдельном
хранилище секретов и не передаваться постоянно работающему backup-контейнеру: для создания копии
достаточно публичного recipient, а закрытый ключ нужен только при явной проверке восстановления.
Каталог `/offsite` подключается через production override Compose; он намеренно не привязан к пути
хоста в основном `docker-compose.yml`.

Внешнее хранилище получит только зашифрованный `age`/X25519-файл `.dump.age` и его SHA-256. Формат
`age` аутентифицирует содержимое: незаметно изменить ciphertext и пересчитать checksum недостаточно,
расшифрование подменённой копии завершится ошибкой. SHA-256 остаётся быстрой проверкой случайного
повреждения до расшифрования. Локальная незашифрованная копия остаётся в закрытом Docker volume для
быстрого восстановления. Если задана
лишь одна из двух переменных или внешнее хранилище недоступно, проход считается неуспешным и
повторяется через короткий интервал. При повторе отправки используется уже созданный локальный dump:
новые копии каждые пять минут не создаются, а локальная retention-очистка продолжает выполняться.
Healthcheck отдельно проверяет свежесть локальной и off-host копий; предел внешней копии задаётся
`BACKUP_OFFSITE_MAX_AGE_SECONDS`. `BACKUP_REQUIRE_OFFSITE=true` обязателен для production: при нём
backup-контейнер и его healthcheck не считаются работоспособными без доступного внешнего каталога и
валидного публичного recipient. Значение `false` оставлено только для локальной разработки.
При `DEPLOYMENT_ENV=production` значение `false` теперь отклоняется ещё до первого дампа и самим
healthcheck, поэтому production-развёртывание не сможет незаметно остаться без внешней копии.

Настоящая проверка именно зашифрованной внешней копии выполняется так:

```powershell
$env:DATABASE_USER = '<DATABASE_RESTORE_USER>'
$env:DATABASE_PASSWORD = '<DATABASE_RESTORE_PASSWORD>'
$identity = (Resolve-Path '.\secrets\backup_age_identity').Path
docker compose run --rm --no-deps `
  --volume "${identity}:/run/secrets/backup_age_identity:ro" `
  -e BACKUP_VERIFY_OFFSITE=true `
  -e BACKUP_AGE_IDENTITY_FILE=/run/secrets/backup_age_identity `
  -e DATABASE_USER `
  -e DATABASE_PASSWORD `
  --entrypoint /usr/local/bin/scheduler-verify-backup `
  backup
```

Команда проверяет SHA-256 и аутентичность зашифрованного файла, расшифровывает его только во
временный файл, восстанавливает отдельную временную БД и сверяет все миграции с текущим образом. Учётная запись,
используемая только для такой проверки, должна иметь право `CREATEDB`; рабочим процессам приложения
это право не требуется. Команда создаёт одноразовый контейнер и подключает закрытый identity-файл
только на время проверки; постоянный backup-процесс его не получает.

Новые копии всегда создаются в формате `.dump.age`. Старые `.dump.enc`, созданные через
AES-256-CBC/PBKDF2, не имеют криптографической проверки подлинности и по умолчанию не принимаются.
Для разового переноса старого архива можно явно передать
`BACKUP_ALLOW_LEGACY_AES_CBC=true`, `BACKUP_ENCRYPTION_PASSPHRASE_FILE=<старый файл>` вместе с
`BACKUP_VERIFY_OFFSITE=true`, проверить восстановление и сразу создать новую `.dump.age`-копию.
Обе legacy-переменные передавайте только одноразовой команде проверки, а не постоянному backup-сервису.
Постоянно включать совместимость с legacy-форматом нельзя.

`postgres-bootstrap` создаёт эту роль вместе с отдельными ролями migrator, bot, admin, site и backup.
Постоянный контейнер `backup` получает только read-only-учётные данные. Скрипт
`scripts/verify-backup.ps1` передаёт более сильную restore-пару из `.env` лишь на время проверки.

Публичный сайт не получает `SELECT` на прикладные таблицы. Его login-роль входит в NOLOGIN-роль
`scheduler_public_reader`, которой доступны только представления `public_site_statistics`,
`public_site_universities` и `public_site_sources`. Агрегированные числа пользователей и подписок
рассчитываются владельцем представления; Telegram ID, профили, обращения, сессии и outbox сайту
недоступны. Каждая новая публичная выборка должна добавляться отдельным ограниченным представлением.

## Масштабирование Telegram-бота

Текущий transport использует long polling. В одном окружении должен работать ровно один экземпляр
`scheduler-bot` с данным токеном: запуск второй реплики приведёт к конкуренции за updates, а не к
отказоустойчивости. `admin` и `site` можно масштабировать отдельно после вынесения сессий и прокси,
но для горизонтального масштабирования бота сначала нужно перейти на webhook и распределённую
очередь обработки обновлений.

## Ротация секретов и история Git

Если `.env` когда-либо попал в Git, сначала отзовите Telegram-токен в BotFather, затем выполните
ротацию пароля PostgreSQL, административного и metrics-токена:

```powershell
.\scripts\rotate-local-secrets.ps1 -RotateDatabasePassword
```

Удаление файла из последнего коммита не отзывает секрет и не очищает историю. После ротации,
согласовав переписывание с участниками репозитория, запустите
`.\scripts\purge-env-history.ps1 -Force`, проверьте результат и отправьте все ветки и теги через
`--force-with-lease`. Остальным участникам нужно заново клонировать репозиторий. CI намеренно остаётся
красным, пока `.env` обнаруживается хотя бы в одной ветке или теге; отдельное правило Gitleaks
распознаёт формат Telegram bot token.

## Хранение и удаление эксплуатационных данных

Один раз в сутки выполняется единая retention-задача. Входящий JSON коннектора очищается через
30 дней, завершённые connector runs — через 180 дней, отклонённые и карантинные снимки — через
90 дней, не связанные со снимками parse logs — через 180 дней, административный аудит — через
365 дней. Неиспользуемые идентичности занятий удаляются через 730 дней; идентичности, связанные с
живым занятием или ручным исправлением, сохраняются. Опубликованные/current снимки и элементы
очереди восстановления не удаляются. В `/metrics` и администраторской команде `/metrics` доступны
полный размер БД и дешёвые размеры отношений PostgreSQL для connector runs и снимков. Эти значения
намеренно приблизительные и не требуют полного сканирования JSONB при каждом scrape.

Экспорт персональных данных включает профиль, подписки, обращения, фактические персональные поля
административного аудита, метаданные активных сессий и ссылки на редакторские/connector-записи.
Хеш токена сессии не экспортируется как защитный credential. При удалении профиля зависимые данные
удаляются, активные административные сессии отзываются, а обязательный эксплуатационный след
получает случайный криптографический идентификатор `deleted:<random>` без вычислимой связи с
Telegram ID; IP и отображаемое имя в аудите стираются. Для администратора сначала нужно снять роль —
случайное самоудаление владельца запрещено.

## Логи и диагностика

Compose ограничивает JSON-логи пятью файлами по 10 МБ. Каждый административный HTTP-запрос содержит
`X-Request-ID`; в журнал пишутся статус, размер ответа, время, IP и идентификатор администратора.
Ответ API с ошибкой возвращает стабильный `code` и `request_id`.

Срок хранения диагностики парсеров в базе ограничен автоматически. Секреты, cookie и заголовки
авторизации в диагностику не записываются. Структурированный журнал дополнительно вырезает токен
Telegram, пароль БД и административные секреты даже из сообщений об ошибках сторонних
HTTP-клиентов.

## Telegram

- `/quiet_hours 22:00-07:00` задаёт интервал без уведомлений, `/quiet_hours off` отключает его;
- встроенный режим позволяет отправить собственное расписание в любой чат через
  `@имя_бота сегодня`, `@имя_бота завтра` или `@имя_бота 08.08.2026`;
- встроенный режим необходимо один раз включить в BotFather командой `/setinline`; серверный
  обработчик уже зарегистрирован;
- напоминания, попавшие в тихие часы, не отправляются с опозданием, а уведомления об изменениях
  расписания откладываются до окончания тихих часов.
